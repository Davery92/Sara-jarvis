</self_check>

**Sara (user-visible response):**

0.6 cosine on a query that should be a near-exact match points to one of three issues:

1. **Vector normalization**: BGE-M3 outputs should be L2-normalized. If the vectors aren't normalized, cosine similarity gives wrong results. Check: `SELECT vector_norm(embedding) FROM episodes LIMIT 5` — if norms aren't ~1.0, the vectors aren't normalized.

2. **Distance metric mismatch**: Your HNSW index uses `vector_cosine_ops`. If you're querying with `<->` (L2 distance) instead of `<=>` (cosine distance), the results will be wrong. Check your query uses `<=>`.

3. **Embedding model mismatch**: If the query embedding and the stored embedding were generated by different models or different versions, similarity will be low. Are you using the same BGE-M3 endpoint for both?

Start with #1 — normalization is the most common cause and the easiest to check.

Query vector not normalized while stored vectors are — classic mismatch. Cosine similarity between a normalized and unnormalized vector gives wrong results. The fix is to normalize the query embedding before the similarity search.

**Sara (user-visible response):**

Stored vectors normalized, query vector not — that explains the low scores exactly. Cosine similarity assumes both vectors are on the unit sphere. When one isn't, the angle calculation is wrong.

Fix: normalize the query embedding before the similarity search. In Python:

```python
import numpy as np
query_embedding = query_embedding / np.linalg.norm(query_embedding)
```

Or in SQL: pgvector's `<=>` operator handles unnormalized vectors correctly for cosine distance. But if you're using inner product (`<#>`) as a cosine approximation, it requires normalization. Which operator are you using?

**Sara (user-visible response):**

Inner product is faster for normalized vectors where it's equivalent to cosine. But if ANY vectors in the pipeline aren't normalized, it gives wrong results. The `<=>` cosine operator handles normalization internally — slightly slower but always correct.

For your workload (50K episodes, single-digit millisecond queries), the performance difference between `<#>` and `<=>` is negligible. Correctness over speed.
